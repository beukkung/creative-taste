# Paired-demo protocol

These are four illustrative paired runs, not a statistical claim about a model or proof of parity with another model.

1. Freeze the brief files and shared input assets before either condition.
2. Produce baseline in a fresh worker context before writing creative-taste. Workers may use normally available skills; log which they actually read. Do not handicap the baseline.
3. Inspect baseline evidence to decide whether this new skill has a useful responsibility. Record observations without relabeling subjective choices as failures.
4. Write the minimal skill, then start fresh workers for the treated condition. They receive the same brief/assets/budget plus the skill. Do not give them baseline output, critique or proposed fixes.
5. One initial implementation plus one verification/repair pass per brief, target 15 minutes, ceiling 20 minutes. Record real duration, repairs, tools/skills and inspection coverage. Over-budget runs remain labeled and cannot be presented as matched-budget wins.
6. Preserve both sources and exports. Record post-run technical repairs by the integration agent separately from the worker budget. A safety/compatibility repair is not an invitation for artistic retouching.
7. Display A/B with randomized sides, no condition names before reveal, and no default winner. Save the user's choices separately from analyst observations. Both players have the same size and controls.
8. Evaluate four held-out briefs only after the skill exists. Keep them separate from the demos used to inform authoring.

## Controls and remaining confounders

Same parent-inherited model configuration and worker type; independent fresh contexts; same shared files; no paid generation. Worker-reported model identity is not independent runtime attestation. Different normally selected skills, variable generation time, stochastic outputs and different instruments/layout choices remain confounders. The treated context intentionally adds creative-taste. The controller has seen both, so its prose critique is not blind. Actual listening/playback and runtime checks must be reported separately from metadata/frame inspection.

## Rubric

For each result cite an element, frame/time or audio measurement when judging: brief fit; hierarchy/focus; coherence; medium-specific craft; technical usability. Score 1–5 only when observed evidence supports it, otherwise leave unscored. A user's preference is not overwritten by an automated score. No aggregate "taste improved X%" claim from these four pairs.
